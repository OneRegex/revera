Revera

One engine source, a machine-checked specification, and consistent APIs across five languages

Overview

Consistent semantics across languages, checked with Lean and cross-language tests

Regular expression libraries differ. Each implementation has its own dialect and feature set, so the same pattern can produce different matches for the same input in different libraries.

These differences become defects when regular expressions process untrusted data. Regular expressions power security tools and filters, and end users sometimes supply the patterns. A match that depends on the implementation is a defect, not a feature.

Regular expressions have no single specification. POSIX.1-2024 defines a current Extended Regular Expression (ERE) standard, which Revera implements across its target languages.

Revera is a clean-room implementation of POSIX.1-2024 ERE. The canonical engine is written in Vego, a strict Go subset built for mechanical translation. A compiler exports it as Vego IR, and printers generate the Rust, Zig, C++, and C engine cores from that IR. Each target adds a hand-written public API and small runtime. All five engine cores are cross-checked against the same corpus for matches, errors, and resource-contract reports.

Beyond cross-language testing, Lean defines formal semantics for Vego, proves that the shipped IR is well-formed, and checks the interpreted engine against a formal ERE model over the corpus and an exhaustive small domain. Before a match runs, a resource contract bounds heap use and abstract work and estimates stack use.

Design

Any number of engines from one source

  1. 1

    Write in Vego

    The engine is written in Vego, a strict subset of Go: no imports, no methods, no interfaces, no function values, no generics. The checker rejects constructs outside the subset and reports the source location.

  2. 2

    Export the IR

    vegoc export turns the source into the Vego IR, stored as revera.vego.json. That release artifact is the input to each generated backend.

  3. 3

    Generate each target

    Each printer lowers the same IR to its target language. Each target also includes an idiomatic, hand-written public API and a small runtime.

  4. 4

    Cross-check the results

    Every implementation runs the same conformance corpus, which covers matches, errors, replacements, iteration, and resource contracts. The make conform command runs the corpus against every backend.

Resource contracts

A resource report computed before a search begins

For a given pattern and maximum input length, Revera reports a heap bound, a step bound, and a stack estimate. Applications can compare the report with a resource budget before running a search.

HeapBytes

The maximum number of explicitly allocated heap bytes for a match on a subject up to the specified length.

StackBytes

An estimate of the deepest stack use, based on fixed frame sizes shared by every target.

Steps

An upper bound on abstract work, counted as one step per loop iteration or function call.

package main

import (
    "fmt"
    "log"
    "os"

    "github.com/oneregex/revera/go"
)

func main() {
    if len(os.Args) != 2 {
        log.Fatal("usage: contract PATTERN")
    }
    re, err := revera.New(os.Args[1])
    if err != nil {
        log.Fatal(err)
    }
    c := re.Contract(4096)
    fmt.Printf("heap: %d bytes\nstack: %d bytes\nsteps: %d\n",
        c.HeapBytes(), c.StackBytes(), c.Steps())
}

The report applies to every subject up to the specified length; it is not a measurement of one run. A nested pattern can report a heap bound in the tens of gigabytes. If a search would exceed the engine's memory capacity, it returns a capacity error while its memory use remains bounded.

Verification

The Lean 4 model and what it proves

Testing covers finite inputs. The Lean development adds machine-checked proofs about the Vego language, the shipped IR, and the POSIX ERE specification itself.

The shipped IR is well formed

The theorems apply to exact, byte-for-byte copies of the shipped engine and probe IR files. Lean decodes both JSON files and elaborates them into a fully typed core, where every name resolves and every operator has a uniquely determined width.

The engine agrees with the specification on checked inputs

The ERE specification is encoded in Lean from the standard text. The engine satisfies that definition for every covered corpus case, and an exhaustive sweep checks every compilation and execution in a small pattern domain.

The generated backends agree on the corpus

The Lean interpreter and every generated backend replay the same corpus. For each covered command, the generated implementations produce the same output as the canonical Go engine.

Phase A heap and step bounds are universal

Phase A of the matcher has universal heap and step bounds, proved by induction for every well-formed program, atom test, and subject. The meter that records those costs is itself proved sound.

The proofs have explicit limits. The corpus and exhaustive checks are finite, not universal. Non-POSIX locale behavior is outside the model. For the capture solver, contract validation is limited to the corpus cases. The Lean README states the exact boundary of each theorem.

Every package embeds the same CLDR and Unicode locale tables, which provide character classes, case mappings, and collating elements for the supported CLDR locales. A compiled engine is read-only and can be shared across threads. Zig callers must use a thread-safe allocator when compiling it.
